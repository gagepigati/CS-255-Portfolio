# CS 255 Portfolio Reflection

## Briefly summarize the DriverPass project. Who was the client? What type of system did they want you to design?

The client for this project was DriverPass. DriverPass wanted a system that would help students better prepare for their DMV driving tests through online classes, practice tests, and driving lessons. The system needed to bring customer accounts, training packages, lesson scheduling, test progress, driver notes, reports, and administrative controls into one centralized system. It also needed to be cloud based so customers and employees could access it through a web browser on computers and mobile devices.

## What did you do particularly well?

I think one thing I did particularly well was taking the information provided by DriverPass and turning it into clear requirements that could later be used in the system design. I separated the functional and nonfunctional requirements and considered what each type of user needed to be able to do. I also carried those requirements into the UML diagrams so that the design stayed connected to what the client originally requested. This helped me understand how requirements gathered early in a project affect the later design decisions.

## If you could choose one part of your work on these documents to revise, what would you pick? How would you improve it?

If I could revise one part of my work, I would improve the technical requirements by making some of them more specific. Some details such as exact response time goals, supported browsers, the cloud provider, database product, and payment service were not provided by the client. If I had more information from DriverPass, I would add measurable requirements for these areas. This would give the development team more specific expectations and make testing the finished system easier.

## How did you interpret the user's needs and implement them into your system design? Why is it so important to consider the user's needs when designing?

I interpreted the user's needs by looking at what each DriverPass user needed to accomplish and then connecting those needs to system requirements and UML diagrams. For example, customers and the secretary needed to schedule, modify, and cancel driving lessons, while drivers needed to view their assigned lessons and record lesson information. The owner needed access to reports and package controls, while the IT officer needed account and access management tools. I used these needs when creating the use case, activity, sequence, and class diagrams. Considering user needs is important because a system can work technically but still fail if it does not actually solve the problems the users have. Keeping the design connected to the users helps make sure the final system provides the features the client asked for.

## How do you approach designing software? What techniques or strategies would you use in the future to analyze and design a system?

I approach software design by first understanding the client's requirements and then breaking the system into smaller parts that are easier to analyze. I think it is important to identify the users, their responsibilities, the information the system needs to store, and the major processes that need to happen. From there, UML diagrams can be used to show the system from different perspectives. In the future, I would continue using requirements gathering, use case diagrams, activity diagrams, sequence diagrams, and class diagrams because each one helps explain a different part of the system. I would also continue checking the design against the original requirements throughout the process so important client needs are not missed.
